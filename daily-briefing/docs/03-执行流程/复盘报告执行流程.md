# 复盘报告执行流程（A股 / 美股通用）

**用途**：记录"用提示词 + 数据源 + 搜索生成一份每日复盘报告"的完整执行逻辑，作为后续手动操作或自动化管道的依据。

**适用范围**：美股日度复盘（`21-美股日度复盘简报(晨间版)-skill.md`）与 A股+港股每日收盘复盘（`22-A股日度复盘简报(收盘版)-skill.md`）通用。

---

## 一、总体流程（5 步）

```
① 明确目标日期
      ↓
② 并行取数（数据 API + 网络搜索 同时进行）
      ↓
③ 交叉核对（多来源冲突处理）
      ↓
④ 按模板生成（数据填进对应模块 + 通俗解读）
      ↓
⑤ 存文件
```

---

## 二、第一步：明确目标日期

| 场景 | 逻辑 |
|------|------|
| 美股 | 北京时间今天早上 → 对应**上一个美股交易日**（如 8/25 周二 → 美东 8/24 周一）。需换算美东/北京时间（夏令时差 12h，冬令时差 13h） |
| A股 | 收盘后复盘当天 → **当日**（15:00 之后） |
| A股+港股 | **必须在港股收盘后（16:00 之后）**，确保 A股（15:00）和港股（16:00）当日数据均完整 |

---

## 三、第二步：并行取数

**核心规则：要数字的用 API/官方，要解释的用搜索。** 两路同时发起，互不等待。

### 3.1 数据 API（提供"确定数字"）

| 数据类别 | 美股 | A股 |
|---------|------|-----|
| 指数/个股行情 | FMP `quote` / Infoway K线 | 腾讯K线（指数，与官方一致）、AkShare |
| 板块涨跌 | FMP `sector-performance-snapshot` | Infoway `plate/industry/CN`（132 行业） |
| 市场宽度 | Infoway `breadth/US` | Infoway `breadth/CN`、AkShare 涨停池/跌停池 |
| 资金流向 | — | AkShare 北向/两融/南向、龙虎榜 |
| 美债收益率 | FMP `treasury-rates` | — |
| 期货/美元指数 | Infoway `common/batch_kline`（ES/NQ/DXY） | 新浪直连（恒指/国企/科技） |
| 国际资产 | 新浪 `hf_CL`/`hf_GC`/`gb_$dji` | 新浪 `hf_CL`/`hf_GC`/`gb_$dji` |
| 龙虎榜/公告 | — | AkShare `stock_lhb_detail_em`、`stock_notice_report` |
| 宏观日历 | FMP `economic-calendar` | FMP `economic-calendar?country=CN` |

**数据路由/冗余原则**（提示词已声明）：
1. **付费商业源优先**（iFinD / FMP / Infoway，字段全、口径官方）
2. 商业源失败/为空 → **自动降级到免费源**（AkShare → 新浪/腾讯）
3. 两者都取不到 → 标 `[待核实]`，用财经媒体检索尽量补充
4. **禁止编造数据**

### 3.2 网络搜索（提供"背景解释"）

| 需要搜索的内容 | 为什么 API 给不了 |
|--------------|------------------|
| 板块热点"主题识别"（光模块"易中天"、玄学"羊概念"） | API 只给行业代码/英文名，不知道"今天炒的故事" |
| 政策（央行 MLF、沪八条）、监管（FCC 传闻） | API 免费档无结构化政策/监管数据 |
| 公司公告解读、财报共识、分析师目标价 | API 不覆盖 |
| 机构观点分歧、舆情话题 | API 不覆盖 |
| 港股通逐股资金、当日板块主题 | API 免费档不覆盖 |

### 3.3 两者互补的例子

- **美股英伟达**：API 给收盘价 $214.72（-0.98%）；搜索给"财报预期 $92B、FCC 风险、HSBC 目标价 $360"——数字归 API，故事归搜索。
- **A股光模块**：Infoway 给 132 行业里的英文行业名；搜索告诉你是"易中天"（中际旭创/新易盛/天孚通信）在崩，因为 FCC + CPO 技术冲击。

---

## 四、第三步：交叉核对（冲突处理）

**规则：官方 > 多数源 > 单一源；拿不准标 `[待核实]`。**

| 实际遇到的冲突 | 处理方式 |
|--------------|---------|
| 英伟达涨跌 -0.98% vs +0.37% | 取多数源 + 官方口径 |
| 板块涨跌（FMP 等权 vs 搜索加权指数） | 两个都对、口径不同 → 标注口径，方向一致 |
| 恒指（新浪返回最新快照 vs 官方 8/24 收盘） | 以官方当日收盘为准，标注时间 |
| Infoway A股指数值偏官方 ~0.8% | 只作交叉验证，不作权威值 |
| VIX（Infoway 17.82 vs 公开 15.13） | 标注口径不一致，`[待核实]` |

**数据接入脚本的产出**：`us_market_data_YYYY-MM-DD.json` / `a_share_data_YYYY-MM-DD.json`，每个模块带 `source` 字段，记录实际来源（用于报告标注）。

## 五、第四步：按模板生成

### 5.1 分工

| 报告层 | 数据来源 | 生成方式 |
|--------|---------|---------|
| 行情/结构层（指数、板块、宽度、龙虎榜、港股、国际资产） | **API 确定值** | 直接填进模板对应模块 |
| 宏观/新闻/事件层（政策、监管、财报预期、机构观点） | **搜索内容** | 做"通俗解读"写入 |
| 每个数字 | — | 配"为什么/意味着什么"解释（提示词的"解释密度"规则） |

### 5.2 模板结构（A股+港股版为例）

```
一、今日一句话 → 二、市场指数与资金流向（A股+港股指数+南向）
→ 三、板块热点（纯A股 6-10个）→ 四、宏观政策 → 五、个股要闻
→ 六、港股收盘联动（港股专属）→ 七、国际市场 → 八、舆情
→ 九、明日追踪清单 → 十、次日/本周展望
```

**关键设计**：A股内容归 A股章节、港股内容归港股章节，互不侵占；两地通过"联动提示"串联（如光模块 AH 同崩、医药 AH 分化）。

## 六、提示词与大模型：从数据到成稿的中间层

### 6.1 三者关系（"菜谱 → 厨师 → 成品"）

```
数据（脚本/API + 搜索）  →  提示词（规范）  →  大模型（执行）  →  报告（成品）
       "原料/佐料"               "菜谱"            "厨师"          "一道菜"
```

- **数据**：脚本产出的 JSON 快照（确定数字）+ 搜索来的新闻（背景解释）——这是"原料和佐料"。
- **提示词**：不负责取数，只定义"报告长什么样"——这是"菜谱"。
- **大模型**：按菜谱、用原料做菜——组织结构、做解读、处理冲突、把控风格——这是"厨师"。

### 6.2 提示词的五个职能（"菜谱"里写了什么）

1. **角色**：定义大模型以"资深财经编辑 / 懂行的财经朋友"的身份写
2. **结构**：报告模板（10 个章节）——决定报告"长什么样"
3. **风格**：解释密度、禁止数据堆砌、通俗"财经朋友"文风
4. **约束**：禁止荐股、风险前置、数据交叉验证、`[待核实]` 标注
5. **数据规范**：数据来源优先级 + 数据路由表——告诉模型"这些数据应该信谁、从哪来"，但**不替模型去取**

### 6.3 大模型的五个决策点（"厨师"做什么）

1. **结构遵循**：严格按模板章节顺序生成，A股归 A股、港股归港股
2. **数字组织**：把 JSON 快照里的确定值填进对应模块
3. **通俗解读**：把数字翻译成人话（"跌 0.8% → 因为芯片股怕财报"）
4. **冲突处理**：多来源数字冲突 → 按"官方>多数>单一"选口径，拿不准标 `[待核实]`
5. **风格把控**：短句、因果链、每数字配解释、不荐股

### 6.4 取数机制澄清：提示词是"清单 + 规范"，不是"调用代码"

**三步骤确认**：

| 环节 | 谁执行 | 说明 |
|------|--------|------|
| ① API 取数 | **脚本/工具**（大模型通过它们执行） | 提示词只给"要什么数据 + 信哪个源"的路由表；真正发 HTTP 请求的是 `fetch_us_market_data.py` / `fetch_a_share_data.py`，大模型是**通过运行脚本**去取数，不是自己直接调 API |
| ② 网络搜索 | **大模型** | 大模型根据提示词涉及的内容/主题（如"光模块、FCC、阿里配股"）发起搜索 |
| ③ 整合输出 | **大模型** | 按提示词的输出要求（模板结构、解释密度、禁荐股）把 API 数字 + 搜索内容整合成报告 |

**机制图**：

```
提示词          →  告诉大模型：要哪些数据（清单）、信哪个源（路由表）、输出长什么样（模板）
                                      ↓
大模型（决策者） →  读清单 → ①跑脚本/工具调 API 取确定数字  ②按提示词主题做网络搜索
                                      ↓
大模型（写作者） →  按提示词的输出要求，把 API 数字 + 搜索内容整合成报告
```

**核心修正**：
- 提示词里的 `data_requirements` 和路由表是**声明/规范**，不是"让模型直接调 API"的指令。
- 取数的执行者因模式而异（见 6.5）：
  - **模式 A（手动）**：大模型自己跑脚本调 API + 自己搜索 + 自己写——既是取数者也是写作者。
  - **模式 B（自动化）**：脚本先独立取数 → 生成 JSON 快照 → 把"提示词 + 快照 + 搜索结果"一起喂给大模型 → 大模型只负责整合输出。

### 6.5 两种运行模式

| | 模式 A（手动，当前） | 模式 B（自动化，未来） |
|--|--------------------|----------------------|
| 谁读提示词 | 我（Claude）——提示词是我的写作规范 | 大模型——提示词 + 数据快照一起喂给它 |
| 谁取数 | 我跑脚本 + 我搜索 | 定时脚本取数 + 大模型联网搜索 |
| 谁写报告 | 我按提示词手写 | 大模型按提示词生成 |
| 数据保障 | 脚本保证数字，我的判断处理冲突 | 脚本保证数字确定性，大模型只负责组织 + 解读 |

## 七、第五步：存文件

- 命名规范：`{市场}复盘简报-{报告日期}(-数据源版|-含港股版).md`
- 每个版本独立文件，不覆盖旧文件，便于对比

## 八、全自动化管道的差异

| 环节 | 手动（当前） | 自动化 |
|------|------------|--------|
| 数据获取 | 我同时扮演"取数+分析+写稿"，脚本 + 搜索并行 | 定时任务（如 16:30）→ 脚本取 API → 结构化 JSON 快照 |
| 新闻层 | 我用 WebSearch | 大模型联网搜索 或 接新闻 API |
| 报告生成 | 我按模板手写 | 大模型按路由表 + 模板合成（负责解读/写作，不猜数字） |
| 关键区别 | 我用自己的判断处理冲突 | 脚本保证数字确定性，大模型只负责组织+解读 |

---

## 九、一句话总结

> **API 负责"是什么"（确定数字），搜索负责"为什么"（背景解释），交叉核对负责"防错"，模板负责"怎么讲"。** 四件事分工明确，最后合成一份报告。
